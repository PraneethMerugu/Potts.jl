# CorePotts execution boundary

CorePotts has one production checkerboard execution graph. A cold Core-owned
compiler lowers each checkerboard color into one ordered LocalMath law:

1. pointwise stages generate proposal geometry and bounded derived keys;
2. gathered proposal evaluation folds Hamiltonian sources in canonical order
   and publishes acceptance or the deterministic scientific failure;
3. a refreshed Core status gate prevents later work after failure;
4. LocalMath resolves owner claims and applies the mutual-maxima conjunction;
5. accepted ordinary effects and tracker reductions evaluate into scratch
   storage, while relationship recurrences evolve package-owned packed shadow
   Fields; and
6. one infallible terminal sequence publishes ownership, trackers, auxiliary
   state, relationship science and generations, status, and reports only after
   every fallible stage succeeds.

All ordinary and relationship evaluators read the immutable stage-entry bank.
Relationship terms retain their original descriptor ordinals even when their
packed representations place them in different banks. Failure in any later
relationship or tracker stage therefore leaves every live scientific
destination unchanged; no in-place ordered recurrence is a transaction
authority.

Once-per-MCS state initialization, optional before- and after-lifecycle laws,
and the Core-owned lifecycle transaction compose around the cumulative color
receipt tail. CorePotts retains bank authorization and publication.

`_CheckerboardExecutionWorkspace` owns this graph. Its single
`CheckerboardExecutionIdentity` is used by capability reporting, checkpoint
validation, replay, queue policy, and settlement. There are no direct,
alternate, adapter, or independently selectable proposal/claim execution
families.

The ownership boundary is intentionally narrow:

- CorePotts owns scientific state, checkerboard topology, RNG addressing,
  Hamiltonian source order and folding, failure semantics, transactions,
  clocks, checkpoint identity, and publication.
- LocalMath owns bounded preparation, submission capacity, provider-lane
  ordering, compiled proposal execution, conjunctive arbitration, publication
  laws, cumulative receipts, lease release, and provider-scope poisoning.
- PottsToolkit supplies fully analyzed concrete plans. CorePotts does not
  resolve biological names, registries, units, or symbolic expressions.

Whole-MCS admission is atomic. CorePotts validates the destination bank,
backend compatibility, workgroup size, logical queue bound, and LocalMath
submission capacities before initializing the destination state or launching
work. Checkerboard execution reuses the same configuration validator before
its first launch.

Eligible before- and after-lifecycle stage groups are prepared as LocalMath
laws and submitted on the cumulative mechanics receipt tail. They introduce
no host callback fence or mid-MCS synchronization. Core lifecycle settlement
remains the explicit domain transaction boundary; requested logical receipts
are cached and released, and a later final settlement is idempotent. Semantic
failures remain receipt-specific, while provider failures poison the
participating provider scope.

The supporting files retain their focused responsibilities:

- `static_evaluator.jl`: concrete expressions, callables, and evaluation;
- `storage_schema.jl` / `storage_runtime.jl`: typed storage and logical state;
- `descriptor_protocol.jl` / `descriptor_plan.jl`: proposal descriptors,
  resource laws, frozen source order, folding, and inspection;
- `domain_resources.jl` / `hamiltonian_runtime.jl`: finite Hamiltonian domain
  resources and before/after proposal views;
- `checkerboard_compiler.jl`: cold Core semantic lowering into the typed
  LocalMath color law, including proposal evaluation, acceptance, owner
  resolution, mutual-maxima selection, and reporting;
- `checkerboard_program.jl`: checkerboard state, lifecycle boundaries,
  cumulative receipt ownership, and whole-MCS preflight; and
- `program_settlement.jl`: the sole checkerboard provider-wait and publication
  boundary.

LocalMath alone decides whether compatible pointwise compiler stages share a
physical launch. CorePotts arranges scientific stages and preserves refreshed
status, conflict resolution, relationship settlement, lifecycle, and final
bank-publication barriers; it owns no separate fusion planner or launch-count
formula.
