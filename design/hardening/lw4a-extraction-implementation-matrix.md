## Purpose

This is the executable traceability contract for LW-4A. It maps the exact reviewed internal module
to a standalone `LocalWorksets.jl` package, every required type/function to tests, and every package,
trust, provider and CorePotts boundary to an acceptance row.

LW-4A is extraction, not capability expansion or API redesign. It does not implement independent,
combined, heterogeneous outputs, general multi-destination work, Level 1 sugar, public candidate
selection or additional backend qualification. Those belong to LW-4B/LW-4C after LW-R2A.

## Target package graph

The repository target is:

```text
PottsToolkit
  -> CorePotts
       -> LocalWorksets
            -> KernelAbstractions
            -> Adapt
            -> Atomix
            -> SHA
```

Forbidden edges are `LocalWorksets -> CorePotts`, `LocalWorksets -> PottsToolkit`, and
`LocalWorksets -> ModelingToolkit/SciML/Metal/CUDA/AMDGPU`. PottsToolkit does not directly use or
re-export the LocalWorksets API merely because it is present transitively.

Julia's active environment, not a dependency's inactive `[sources]` table, controls unregistered
path resolution. Therefore every independently activated development/test environment must name
its required local path, and manifests are regenerated by `Pkg` rather than hand-edited. This
follows the current official [Pkg project/source rules](https://pkgdocs.julialang.org/v1/toml-files/)
and Julia 1.12 [workspace test guidance](https://pkgdocs.julialang.org/v1/creating-packages/).

## Central admission and trust matrix

LW-4A must replace the literal CorePotts UUID allow-list. Copying that list and swapping in a new
UUID is insufficient evidence by itself.

The accepted design requirement is a package-owned closed admission root:

- all executable lowerings and provider calls resolve to package-defined methods or exact internal
  primitives;
- central code uses exact `invoke` boundaries or verifies the resolved `Method` against immutable
  package-owned identity before calling it;
- cached prepared callbacks are revalidated after Julia world-age changes;
- named downstream adapters that require a trusted lifecycle boundary exact-invoke the accepted
  public signature and revalidate its stored package-owned `Method` after world changes;
- public/external declarations are data and cannot install a launch method;
- environment qualification is inert reviewed data consumed only by central provider code; and
- the closed boundary begins after entry through package-owned lifecycle methods and the named
  trusted CorePotts adapter. Julia's mutable global method table cannot seal arbitrary callers
  that choose ordinary public dispatch; deliberate exact-signature replacement or malicious
  `Core.eval` inside the same Julia process remains outside the threat model and is detected at
  the next trusted world-change validation when it affects a prepared boundary.

| ID | Security requirement and attack |
|---|---|
| S01 | More-specific external `_central_admission`, topology fingerprint or provider-identity methods cannot change planning. |
| S02 | More-specific external lowering evidence, binding derivation, workspace, preparation, execution or inspection methods cannot be selected; exact concrete submission/binding specializations remain package-owned and world-checked. |
| S03 | External atomic/value capability methods returning `true` cannot authorize a type/operation/address-space tuple. |
| S04 | External provider-adapter or wait methods cannot introduce a backend, host fallback, hidden synchronize or native event; exact backend/device/owner-task adapters share the qualified cumulative completion/failure scope. |
| S05 | Replacing a method after planning/preparation is caught before the next launch by cached method/world validation. |
| S06 | Forged `WorkPlan`, `PreparedWork` and `WorkEvent` constructors remain inaccessible without internal construction authority. |
| S07 | Prelaunch schema/world/method-owner/dispatch rejection does not poison; any actual or conservatively uncertain failure after entering an admitted lowering poisons every preparation in the exact shared provider scope, whether observed synchronously at launch or asynchronously at the qualified wait boundary. |
| S08 | Source scan contains no CorePotts UUID/name, external trust registry, mutable global ownership registry or extension self-registration path. |

Any S01–S08 failure is P1; an actual unauthorized launch, fallback, false capability or missed
backend failure is P0.

## Implementation order and hold points

1. **E0 — Freeze and scaffold**
   - re-hash the exact LW-R1 source/test/runner boundary;
   - create the package project/workspace/module skeleton and new UUID;
   - resolve environments with `Pkg`;
   - run isolated load and dependency tests.
2. **E1 — Copy and mechanically partition**
   - copy substrate/lowerings/provider/evidence into the package;
   - preserve exact public inventory and behavior;
   - make standalone unit/conformance tests pass before changing CorePotts.
3. **E2 — Replace trust/admission root**
   - remove the literal CorePotts UUID allow-list;
   - implement the package-owned closed boundary;
   - pass S01–S08 in fresh processes, with hostile tests last.
4. **E3 — Rebind CorePotts**
   - add the dependency and import the module;
   - adapt only namespace/public-interface references;
   - pass C01–C08 and the complete CorePotts CPU suite.
5. **E4 — Remove duplicate nested source**
   - prove no active include/reference remains;
   - remove old files only after standalone and Core tests pass;
   - re-run duplicate/source/path inventories.
6. **E5 — Full CPU and real-Metal qualification**
   - run C09–C12, Q01–Q08 and every required command;
   - record exact hashes, launches, waits, workspace, allocation, cache and throughput.
7. **LW-R2A — Fresh package-boundary committee**
   - no LW-4B implementation begins before clearance.

Each hold point is revertible and keeps the frozen direct CorePotts path. A later failure reopens the
earliest owning hold rather than being worked around in a downstream package.

## Severity and stop rules

- **P0:** wrong result, unauthorized/host execution, unsafe lifetime/alias behavior, false
  determinism, missed provider failure or partial scientific publication.
- **P1:** domain dependency/leak, copied Core UUID trust, bypassable admission, false backend claim,
  hidden wait/allocation/transfer, changed checkpoint identity, missing exact test row or direct-oracle
  regression.
- **P2:** API diagnostic, inspection, docstring, file organization or maintainability defect that
  does not change execution.

Any P0/P1 stops the owning hold. P2 requires an explicit disposition before LW-R2A. Evidence or
admission rules may not be weakened to make extraction pass.
